# 드래그·스와이프 및 가독성 검수

현재 3차 UX는 [별도 기록](./UX_V3.md)을 참고하세요. 기존 네 뷰포트 제스처 검사를 유지하고 인트로·9개 카테고리·원형 점수·제품 상세·AI 설명·내 정보 흐름을 추가했습니다. 클릭 가능한 이미지에서 드래그가 상세 열기로 이어지는 회귀는 `BrowseButton`의 이동 거리 검사로 수정했습니다. 네이티브 dialog의 배경 스크롤 잠금은 열려 있는 동안에만 적용하고 닫으면 원래 스크롤과 포커스를 복원합니다. 아래는 2차 원인과 검수 기록입니다.

## 재현한 원인

화면 전환의 `motion.main`이 `translateY`를 적용하면서 안쪽의 `position: fixed` CTA에 새로운 containing block을 만들었습니다. 전환 중에는 버튼의 기준이 뷰포트에서 main으로 바뀌고, 전환 종료 시 다시 바뀌었습니다. 기존 방식에서 전환 프레임의 transform/고정 버튼 경계 검사가 실패한 뒤, 수정 후 같은 검사가 통과하는 것으로 확인했습니다.

제품 이미지는 기본 HTML drag가 켜져 있어 마우스 드래그 시 브라우저의 이미지 드래그 그림자가 생겼습니다. 이를 앱 드래그 인터랙션으로 사용하지 않으므로 해당 이미지에만 `draggable=false`, `-webkit-user-drag: none`을 적용했습니다. 텍스트 선택은 유지합니다.

카테고리 목록은 의도된 가로 스크롤 영역입니다. 넘침의 전파를 `overscroll-behavior-x: contain`으로 한정하고, 나머지 주요 콘텐츠는 세로 팬과 핀치 줌을 허용합니다. 루트의 수평 overscroll만 억제합니다. `body { overflow: hidden }`, 전역 touchmove 차단, 드래그 이벤트로 좌표를 강제하는 방식은 사용하지 않았습니다.

제품 비교의 작은 이미지 컨테이너도 실제로 축소될 수 있도록 `flex-shrink`/`max-width`를 수정했습니다. 긴 텍스트는 부모 폭 안에서 줄바꿈합니다. `100vw`나 앱 전체를 움직이는 drag 속성은 없습니다.

## 수정 범위

- `src/App.tsx`: main은 opacity 전환만 사용. 고정 버튼의 조상에 transform이 생기지 않음.
- `src/App.css`, `src/index.css`: 컨테이너 폭/최소 폭, 이미지 축소, 줄바꿈, 제스처의 범위, 글꼴 크기와 간격.
- `src/screens/Home.tsx`, `src/components/ProductImage.tsx`: 기본 이미지 드래그 비활성화.
- 결과·비교 화면의 개별 등장 모션, 제품 추가/삭제 모션, 게이지 애니메이션과 reduced-motion 대응은 유지.

## 타이포그래피와 간격

Pretendard, 화이트/쿨그레이/더스티 블루를 유지했습니다. 화면 제목 28px, 제품명/중요 항목 17px, 상세 섹션 제목 20px, 본문 15~16px, 주요 버튼 16px, 보조 설명은 주로 13~14px입니다. 작은 수량 배지와 이미지 안의 표식은 예외입니다.

일반 화면 상단 padding 68→36px, 홈 제목 앞 간격 58→34px, 검색 간격 25→18px, 제품 행의 고정 최소 높이 제거, 결과 게이지 244→216px, 카드 간격 11→9px로 조정했습니다. 데스크톱의 의미 없는 최소 844px 고정 높이는 뷰포트 기반으로 바꿨습니다. 하단 CTA와 내비게이션에 필요한 스크롤 여유는 남겼습니다.

## Playwright 범위

`tests/layout.spec.ts`:

- 390×844, 375×667, 320×568, 1440×900
- 홈·탐색·조합함·결과·최적화·보관함의 마우스 드래그
- 모바일 Chromium CDP의 실제 touchStart/move/end로 좌우/세로 스와이프
- 카테고리 안에서만 가로 스크롤, 문서 scrollX=0, 가로 넘침 없음
- 긴 화면에서 세로 스크롤 유지
- 전환의 매 프레임에서 고정 버튼 경계와 조상 transform 검사
- 이미지의 기본 draggable 해제

데스크톱에서 연속적인 가로·세로 wheel 이벤트를 보내면 Chromium이 이전 축의 wheel gesture를 유지합니다. 별개의 사용자 제스처로 검사하도록 종료 간격을 둡니다. 이것을 앱의 세로 스크롤 차단으로 오판하지 않습니다.

`tests/analysis-flow.spec.ts`는 동일한 네 크기에서 교체 선택→비교→확정→재계산 결과→보관→조합함→새로고침까지 검사합니다. 이 검수는 Chromium 터치 에뮬레이션이며 실제 iOS Safari 기기 검증을 주장하지 않습니다.

스크린샷: `docs/qa/layout-*.png`, `updated-result-*.png` 및 기본 화면 이미지. 배포는 하지 않습니다.

최종 결과: 4개 뷰포트의 제스처 테스트와 이미지 drag 검사 5개 통과. 전체로는 단위 33개 + E2E 32개, 총 65개 통과. 빌드 성공, lint 경고·오류 없음.

320×568 홈에서는 세로 공간에 맞춰 히어로 비율과 간격을 추가 조정했습니다. CTA 하단 459px, 내비게이션 상단 487px으로 초기 화면에서 가림 없이 표시됩니다. 긴 탐색·분석·비교 화면의 세로 스크롤은 계속 동작합니다. `home-small-before.png`와 `home-small-after.png`로 전후를 기록했습니다.

데스크톱은 앱 프레임을 뷰포트 높이에 맞춘 실제 세로 스크롤 컨테이너로 구성했습니다. 긴 콘텐츠가 고정 하단 버튼 뒤의 프레임 밖으로 보이지 않습니다. 모바일은 기존 문서의 세로 스크롤을 유지합니다. 화면 전환 시 현재 스크롤 컨테이너도 맨 위로 돌아가며, 프레임 스크롤과 고정 버튼의 전환 안정성을 함께 검사합니다.

이 변경 후 전체 65개 테스트, build, lint가 다시 통과했습니다. 네 뷰포트 × 여섯 화면의 실제 앱 내부 `scrollWidth - clientWidth`를 별도로 측정한 최대값도 0px입니다. 루트 넘침을 숨겨서 통과시킨 결과가 아닙니다.
